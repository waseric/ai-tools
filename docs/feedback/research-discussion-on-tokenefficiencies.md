What Compaction Actually Does
Every message you send, every response from Copilot, every tool call and its result, and the system instructions that define Copilot's behavior are all held in a context window — the total amount of information the model can consider at one time when generating a response. GitHub
As a conversation grows, the accumulated messages and context can fill up the model's context window. Context compaction summarizes the conversation history to free up space, so you can continue working in the same session without losing important details. When the context window fills up, VS Code automatically compacts the conversation by summarizing earlier messages. This happens transparently in the background, so you can keep chatting without interruption. Visual Studio Code
In other words, compaction is lossy summarization — the raw message history is replaced with a condensed prose summary generated by the model. The conversation history is compressed into a much smaller summary, freeing up the majority of the context window for new work. Copilot uses this summary to maintain continuity — it knows what was discussed, what was decided, and what to do next — even though the original messages have been replaced. GitHub
The alternative would be worse: without compaction, once the context window filled up, Copilot would have to fall back to simply dropping old messages from the conversation history — removing them without any summary or record. GitHub

What Triggers It
When your conversation reaches approximately 80% of the context window's capacity, Copilot CLI automatically starts compacting the context in the background. The VS Code extension behaves similarly, and you can also trigger it manually with /compact in the chat input — and even guide it, for example: /compact forget about all variants, except the rust version. GitHub

The Risks to Session Effectiveness
1. Fine-grained detail is lost
Compaction is a summarization process, so some detail is inevitably lost. The summary captures the key points, but fine-grained details — such as the exact wording of every message, the full output of every command, or minor decisions made early in a long conversation — may not be included. If you need Copilot to recall a very specific detail from much earlier in the session, it may not have that information after compaction. GitHub
2. Repeated compactions degrade quality over time
Each compaction summarizes a summary-of-a-summary, compounding information loss. If the conversation has gone through many compactions, important context can be progressively lost in the summarization process, to the point where starting a fresh session is preferable. GitHub
3. The "lost in the middle" effect
Even before compaction hits, high context fill degrades response quality. As one GitHub issue notes, a developer at 160k/200k tokens may notice the model repeating tool calls or re-reading already-processed files — a known degradation correlated with the "lost in the middle" effect at high context fill.
4. Compaction quality is unpredictable
The summarization is itself a model-generated output, meaning what gets preserved is partly a matter of what the model judges important, not necessarily what you consider important. Early architectural decisions, subtle constraints, or rejected approaches may get dropped silently.

Practical Guidance

Watch the context bar — VS Code shows a visual fill indicator so you can see how close you are before compaction triggers.
Compact manually and early if the conversation has drifted or accumulated noise, rather than waiting for auto-compaction.
Start a new session when switching to an unrelated task, or once the session has been compacted multiple times and you sense the model is losing coherence.
Re-state critical constraints explicitly after a compaction if precision matters — don't assume the summary captured everything.

Here are the main techniques, organized by what they're actually doing:

Instruct the Model to Read Before Acting
The simplest and most impactful pattern: explicitly tell the model to read and internalize first, then respond. Without this, models tend to interleave reading and generation, which wastes tokens on "thinking out loud" that doesn't need to be in context.

"Read the entire file before writing any code."
"Understand the full scope before proposing a plan."
"Do not respond until you have reviewed all attached context."


Request Compressed Intermediate Reasoning
Chain-of-thought is powerful but verbose. You can ask for dense scratchpad rather than narrative reasoning:

"Think in bullet points, not prose."
"Use abbreviations freely in your reasoning steps."
"Summarize your understanding in 3 sentences before proceeding."

This keeps the reasoning that needs to be in context short without eliminating it.

Ask for Structured State Tracking
For long multi-step tasks, ask the model to maintain a compact running state object rather than restating context in full each turn. This is especially useful in agentic sessions:

"Maintain a JSON state block at the top of each response with: current goal, completed steps, open questions, key constraints."
"Track decisions made so far as a numbered list; don't re-explain them."

This front-loads important information where attention is strongest and avoids it being buried in prose history that compaction may lose.

Separate Reading Passes from Writing Passes
Explicitly staging the task reduces redundant context. For example:

"Pass 1: Read all files and output only a summary of what's relevant to the task."
"Pass 2: Using only that summary (not the raw files), implement the change."

This is particularly valuable because raw file content is token-expensive in context; a targeted summary of the same content may be 10–20x smaller and equally useful for generation.

Use XML or Structured Tags to Bound Context
Models can be instructed to emit and attend to tagged sections rather than free prose, which makes summarization during compaction much more reliable:
<decision>Use PostgreSQL over SQLite due to concurrency requirements</decision>
<constraint>Must not break the existing auth API contract</constraint>
<status>Scaffolding complete, tests pending</status>
When compaction eventually runs, these tagged facts are much easier for the summarizer to preserve faithfully than decisions buried in conversational prose.

Instruct Proactive Forgetting
Tell the model explicitly when prior context is no longer needed:

"Discard all context about the SQLite approach — we're committed to PostgreSQL now."
"The scaffolding discussion is resolved; don't carry it forward."

This is the manual analog of what /compact does, and doing it early keeps context lean before auto-compaction is forced.

Minimize Re-Stating of Known Context
Models often re-summarize what they "understood" before answering, which is polite but token-expensive. You can suppress this:

"Do not restate what you've been told. Begin your response with the first substantive output."
"Skip acknowledgment. Go straight to the answer."


Prioritize Early Placement of Critical Facts
Attention is strongest at the beginning and end of the context window ("lost in the middle" is a real, documented phenomenon). When giving the model important constraints or decisions:

Put them in the system prompt or at the very start of the first user message, not buried mid-conversation.
Repeat critical constraints briefly at the start of major new phases of work rather than assuming they survived intact from 20 turns ago.


The Meta-Principle
All of these techniques share a common logic: context window space is a scarce resource, and the model is not automatically incentivized to conserve it. Explicit instructions that reduce verbosity, stage information processing, and structure outputs for survivability through compaction are the primary levers you have. The model will follow these instructions quite reliably when they're stated clearly — it just won't apply them by default.
